# 工作流契约

[English](/.agents/se/contracts/workflow.md) | 中文

> 开发工作流的操作性文本：请求如何分类、历史如何保留、什么有约束力而什么没有、交付如何校验、门禁何时按什么顺序运行。它自足；它要求的任何东西都不在安装后的 `.agents/` 树之外。

安装本契约的仓库可以仅凭它运行完整的开发流程：入口指令概括这些规则，技能按需施用，同级契约补充更细的格式。摘要与本页冲突时，流程以本页为准。

## 目的与安装树

本契约管辖已安装 kit 的仓库中的每一个请求：如何分类、提案与讨论、回复与实现事件如何保留、人何时裁决、交付必须包含什么，以及由哪些校验决定验收。

它周围的安装树是固定的。`.agents/se/contracts/` 存放本契约与同级契约；`.agents/se/templates/` 存放记录模板；`.agents/se/scripts/decisions/` 与 `.agents/se/scripts/docs/` 分别放工作流与双语组件的校验器；`.agents/skills/` 放各组件的技能。未安装的组件不贡献任何东西，本契约没有一条规则依赖未安装的组件：配对门禁是唯一按条件进入的门禁。

消费者在 `.agents/notes/` 下维护自己的决策树；该树下没有任何文件随 kit 分发。全篇术语：**请求**是一次带历史的变更；**记录**是陈述约束的提案配对；**证据**是非约束性的讨论或回复；**交付**是变更加上改写后的记录；**门禁**是决定部分验收的校验器。

指令、校验器根路径、示例与模板占位符中的记录树路径指向目标仓库自己的记录，允许出现在安装载荷中。载荷不得依赖 se-tools 的开发历史：安装代码时移除源码决策锚点，并在安装写入任何内容之前拒绝指向记录树的具体 Markdown 链接。自安装使用相同的渲染方式；se-tools 开发者通过组件源码追溯开发决策。

<a id="layers"></a>

## 规则分层与提升判据

规则只有放在它所属的层才生效。**放错登记层的规则等于不存在：** 常驻块里的格式细节每次会话都要付成本，按需技能里的常设约束在需要时并不在生效。

| 登记层 | 内容 | 何时加载 | 判据 |
|---|---|---|---|
| 常驻 AGENTS.md 块 | 任何情境选择之前就必须成立的规则：决策在哪里、注释里的决策路径意味着什么、冲突时以哪一方为准、请求分类 | 每次会话 | 每一行都是常驻上下文成本 |
| 技能 | 带事件触发、步骤与产物的流程 | 按需 | 触发事件唯一且可判别 |
| 契约与清单 | 技能内部的更细规则：格式、门禁行为、清单 | 技能加载之后读取 | 没有独立触发 |
| 决策记录 | 决策本身，在消费者自己的树里 | 按需 | — |

**提升判据**：新能力默认作为契约，或作为既有技能的一节。只有当**触发事件、输入对象与产物三者都独立**时才提升为技能。任何内容都不进入常驻块，除非它必须在任何情境选择之前成立。

<a id="classes"></a>

## 请求分类

动任何东西之前先分类；分类决定实现能否开始。

- **纯实现。** 约束成立，只换做法。直接做；提交序列从 `impl:` 开始；不需要提案文件夹。
- **决策变更或新决策。** 变更新增、放宽或推翻一条约束。写任何代码之前先写提案，对照现行决策检查，出现违反或不确定就停下等人裁决。
- **不清楚。** 先查清这次变更实际触及什么、落在哪些约束之下，再归入上面两类之一。

<a id="history"></a>

## 分支与事件历史

改文件之前从 `main` 建一个分支，命名为 `<type>/<slug>`：type 描述请求（`feat`、`fix`、`chore` 等），slug 是简短的小写连字符摘要。分支类型描述请求；提交主题描述事件。

在首个请求提交的 body 里记录起始集成提交 `Base-SHA: <sha>`。该 SHA 固定不动：不要从移动的 `main` 重新计算基线。

提交主题写成 `tag: description`，一个提交一个完整事件：

| 主题 | 事件 |
|---|---|
| `proposal:` | 初始提案或实质性提案修订 |
| `discuss:` | 记录进仓库的评审者或用户意见 |
| `reply:` | 作者回应与处置，本次提交不含提案修改 |
| `reply & revise:` | 作者回应连同它引起的提案修订 |
| `decision:` | 事后记录的人工批准、否决、延期或重启 |
| `impl:` | 实现，含配套测试与文档 |
| `review:` | 实现评审发现与结论 |
| `fix:` | 评审或校验之后的修正 |

`reply & revise:` 同时携带回复与它引起的提案改动；`reply:` 只携带回应。两种情况下回复文件都按讨论的 slug 命名为 `reply-<slug>`。

提交一旦与评审者共享或作为评审引用，就只追加：用后续提交修正，绝不 amend、rebase 或 squash。集成时通过普通 merge 或 fast-forward 保留原始提案、讨论与实现提交；禁止 squash 合并。任一合并方向上，解决冲突的提交用 `fix:`，干净的合并用 `impl:`。

用 `git log --reverse --oneline <base>..HEAD` 读取事件序列，用 `git show <sha>` 查看单个事件。

<a id="records"></a>

## 记录、证据、批准与生命周期

只有提案配对具有约束力：`proposal.md` 与 `proposal.zh.md` 陈述候选或已交付的约束。`discuss-*` 与 `reply-*` 文件即使位于 `implemented/` 内也是非约束性证据；它们记录评审与回应，从不因所在位置获得权威。

批准发生在人与提案作者之间的直接对话中。任何仓库产物、门禁结果或签名都不证明它；agent 从不虚构批准，agent 之间的一致是建议，不是授权。

生命周期是目录，不是字段：`proposed/`、`implemented/`、`rejected/` 与 `archived/`。已批准但未完成的记录留在提案；延期的记录也留在提案。被否决的记录在状态行写明一句话理由并冻结正文；归档的记录冻结，且不再作为现行行为的依据。

交付把整个请求文件夹——提案配对、证据三件组与 chain 文件——移到 `implemented/<class>/`，并把固定的 `proposal.md` 从提案章节改写为已落地的决策章节，把验收标准与风险折进后果。同一次变更修复入链、切换行与配对记录；Git 历史与逐字引文保留原路径与原话。

`decision:` 提交可以在事件发生之后标记它；它是标记，不是批准证明。

<a id="citations"></a>

## 证据引用

有证据的每个请求文件夹都带一份 `chain.yaml`，记录事件坐标：每个事件记下提交与决策记录路径，只存一个英文锚点，中文路径由加 `.zh.md` 派生。讨论与回复头部本身只携带 `Chain` 与 `Author`；坐标在 chain 文件里，不在证据头部。

证据正文以 `Chain <ref> L<a>-L<b>` 标记具体行段：`<ref>` 指同文件夹的文件名，行段按引用文件的语言读取。形如 `<request>/<thread>/<discuss|reply>/<ref>` 的完整 ID 由安装后的 chain 解析器 `.agents/se/scripts/decisions/chain.py` 解析；它提供只读的 `refs`、`show`、`diff` 子命令与 `add`、`modify`、`delete` 编辑子命令，编辑命令默认 dry-run，除非传入 `--write`。

chain 是经文档门禁校验的历史证据地址，不是批准，也从不证明讨论已解决。冻结文件夹的 chain 文件不被改写：冻结的证据保留原地址。

<a id="reading"></a>

## 读取现行决策

改变行为之前先读决策：`.agents/notes/implemented/` 下的已落地记录是现行约束，`.agents/notes/proposed/` 下的开放提案是候选约束，本次变更可能需要满足或修订它们。

代码注释里的决策路径就是那段代码的决策；改代码之前先读该记录。

任务与记录冲突时，以决策为准，并把冲突报告出来，不要抹平。若记录本身错了，那是一次决策变更，要有自己的提案与人裁决——不是实现层面的选择。

不要用记忆代替记录，也不要把注释里的复述当作完整约束；记录才是权威。既有扁平记录继续有效。

<a id="warranted"></a>

## 什么情况下才写决策记录

只问一个问题：这次改动改变了「必须一直满足什么」吗——新增约束、放宽约束还是推翻约束？修 bug 暴露出我们本来就该满足的约束，算。纯实现替换、机械改动或局部 UI 调整，不算。

只有答案为是时才写记录：记录树的量级停在决策数，不停在提交数。一条记录陈述一条可独立判定违反的约束，并记录它打败的真实备选。

记录自身的格式、证据格式与示例规则由格式契约规定；机器查不了的判断在复查清单里。两者都在本页最后一节点名。

<a id="bypass"></a>

## 绕过标记

只有用户为本次变更明确要求时才跳过决策流程。在提交信息里记录 `Decision process: bypassed (reason: …)`。

绕过不是违规，也不放宽交付：历史仍然只追加，交付产物仍然通过门禁。绕过率是值得关注的信号。

<a id="delivery"></a>

## 交付

决策变更只有经过人裁决并门禁全绿才可交付；集成遵循用户对发布或合并的授权。

交付约束本身，而不只是文字：让约束成立的代码、测试与文档，移动并改写为已落地章节的记录，以及同一次变更中修复的链接与配对记录。

删除请求分支之前，通过普通 merge 或 fast-forward 把它的原始提交保留进 `main`。不要为了保留证据而合并未完成的实现：把分支推到远端，直到有授权的保留安排保住这些提交。压缩快照不能替代被保留的历史。

<a id="validation"></a>

## 交付校验

交付校验只根据被跟踪的仓库产物、适用的契约，以及契约明确要求的 Git 对象来决定验收：证据引用的 `commit:path` blob，与显式的 CI 比较基线。

安装清单是安装状态，永远不是证据。会话日志、插件或 profile 状态、工具调用序列与 agent 推理都不得作为合规证明。分支拓扑、提交主题与人工批准仍是过程义务，由人评审，不是交付门禁。

校验器是被跟踪内容、契约要求的 Git 对象与显式比较基线的确定性函数：不联网、不读时钟、不用随机数、不依赖环境。它们可以因格式、双语配对、链接、证据引用、构建、类型与测试而阻断集成或发布。

绿色结果不能确立人工批准、决策正确性或审阅者同意。

`decision-check` 保持建议性：它标出违反与不确定，供人裁决，绝不成为 CI 的批准门禁。

仓库新增的检查必须提交且只做加法：可以增加覆盖，但不能停用核心校验器；每个门禁都保留自己的未自动检查声明，打印它实际选择了什么、跳过了哪些检查。

产物校验无法证明每一项过程义务都被履行；工作流陈述这一限制，而不是承诺机器证明。

<a id="gates"></a>

## 门禁顺序与未自动检查声明

门禁按顺序运行，各自独立，互不调用：

1. 双语配对门禁，仅在安装双语组件时运行；
2. 文档门禁；
3. 链接门禁。

绝不把门禁合成一个会掩盖失败的脚本，也绝不让一个门禁调用另一个：分开运行才能让每处失败可归因。

本地门禁用 `--staged` 检查索引与 `HEAD`。CI 必须显式给出比较基线，用 `--base <sha>` 传入；缺失、为零或不可解析的基线是错误，绝不是被静默跳过的检查。

每次运行都以声明它没检查什么结束。读那条声明并复查那些项：门禁全绿既不证明人工批准，也不证明审阅者同意。

安装后的 workflow 组件 AGENTS.md 块写有已安装校验器的确切命令与路径；本契约只点名门禁，不链接命令。

<a id="authority"></a>

## 权威与冲突

在 kit 的源仓库中，决策记录高于本契约；两者的不一致是缺陷，须在同一次变更中修复，且记录保留本契约所概括的理由。消费者只读安装树，因此它必须服从的记录是它自己的记录。

在已安装的消费者仓库中，本契约是操作权威：kit 源仓库的任何决策历史都不随之分发，消费者在自己的树里记录自己的决策。

对分发规则的修改，在同一次变更中更新陈述该规则的决策与本契约；改变约束的契约改动需要自己的提案。既有项目指令被保留而不是被覆盖：暴露冲突，不要静默解决。
