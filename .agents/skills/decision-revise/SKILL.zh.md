# decision-revise：记录落库

[English](/.agents/skills/decision-revise/SKILL.md) | 中文

**所有写入都从这里经过。** `decision-intake`、`decision-check`、`decision-audit` 只读。

写任何条目之前，先读[记录格式契约](/.agents/se/contracts/note-format.zh.md)。

## 不变量

1. **一条决策一个请求文件夹，`proposal` 配对是唯一记录。** 不用编号，不重排，跨引用一律用链接。
2. **目录即状态。** 状态变化是 `git mv`，不是改字段。
3. **决策变了就是新记录。** 修订 `implemented/` 下的记录只允许更新**事实**（路径、名称、机制），不允许把决策改写成它的反面——那是新记录 + 双向链接。
4. **沿革不手写。** 历史由 git 承载；想说明「取代了谁」，在正文里写一行双向链接，不要维护 `r1 / r2` 链。
5. **动作前先判定 `J1`。** 只有决策变化才写（见[评审清单](/.agents/se/contracts/review-checklist.zh.md)）。纯实现替换、机械改动不写。

## 初始化（绿地项目）

1. `git rev-parse --show-toplevel` 确认仓库根。若决策树已存在，改走下面的 `bootstrap`。
2. 安装器写入带标记的 `AGENTS.md` 块。仓库没有 `AGENTS.md` 时，写一份最小地图，点名已装的[工作流契约](/.agents/se/contracts/workflow.zh.md)与决策树；已有 `AGENTS.md` 不覆盖——冲突时报告给用户，不要静默合并。
3. 建立骨架：按[记录格式契约](/.agents/se/contracts/note-format.zh.md)的路径形状创建 `{lifecycle}/{class}/` 目录。
4. 装门禁（pre-commit）：按序跑双语配对门禁、文档门禁、链接门禁；具体命令与路径见 gate 与 bilingual 组件安装的 `AGENTS.md` 块，双语配对门禁只在 bilingual 组件已安装时存在。
5. 用户当场明确的约束，逐条走下面的「新增」。**不知道的不要补写。**

## 请求、讨论与交付

遵循[工作流契约](/.agents/se/contracts/workflow.zh.md)；完整格式只在[记录格式契约](/.agents/se/contracts/note-format.zh.md)，起草形状见[模板](/.agents/se/templates/)。同一请求在一个分支完成，首提交 body 记录固定 `Base-SHA`。独立约束用多个互链文件夹。提案作者维护 proposal，审阅者用独立讨论文件；作者逐 ID 回复同 slug 讨论；讨论与回复的头部只写 `Chain` 与 `Author`，引用坐标写在同文件夹的 `chain.yaml`，正文用 `Chain <ref> L<a>-L<b>` 标记具体引用行段，`chain.py` 可解析完整 ID；`reply & revise:` 同时含回复及提案修改，只有回复则 `reply:`。审阅者不能改作者回复，作者不能改审阅者立场；交接或代为规范化必须署名。

人直接批准具体版本后才能实现。获批但未交付仍在 `proposed/`；交付时移动整个文件夹，固定 `proposal.md` 文件名，改为已落地章节，修复当前入链、切换行、配对记录并刷新回复摘要。已批准正文的其他修改需要重新批准。拒绝注明原因并冻结正文，延期仍 proposed，归档冻结整个文件夹。直接对话的批准不要求 ruling 文件或提交；报告是只读派生输出，保留分歧和未经确认的作者闭合，不充当批准。

本地 hook 使用 `--staged` 检查索引；CI 严格运行并显式传 `--base <sha>`。共享或引用过的提交不 amend/rebase/squash，正常 merge 或 fast-forward 保留原提交。干净 merge 用 `impl:`，冲突解决用 `fix:`。删除分支前保留原提交；未完成实现不可为保存证据而合并，需保留已推送分支直到授权安排落实。发布与合并遵从用户授权。

## 新增

1. 判定 class（见契约 P3）与目标生命周期。
2. 取首次提出日期（当天；迁移来的从 git 历史取），起 slug。
3. 在决策树里建 `<lifecycle>/<class>/<yyyy-mm-dd>-<slug>/` 文件夹，创建 `proposal.md`、`proposal.zh.md` 和 `proposal.i18n.yaml`；在 proposal 头部标明稳定作者角色或 handle。既有扁平记录与归档不迁移。
4. 按契约写全章节。**`## 问题` 一节必须分 `**现象**` 与 `**代价**` 两层。**
5. 若已有实现，补代码锚点（见[锚点约定](/.agents/se/contracts/anchor-convention.zh.md)）。
6. 跑文档门禁与链接门禁。

## 修订

1. **改事实**：路径、符号、默认值、机制变了，就地改掉。没有历史，只有现状。
2. **改决策**：不在这里做。新建一篇记录，两篇互链（`取代 <链接>` / `被 <链接> 取代`），旧篇按「归档」或「合并」处理。
3. 涉及作用域变化的，重新检查是否有其他记录因此冲突，交用户裁断。
4. 检查为旧约束特化的防御、桥接、兼容分支，提出保留或重构建议——**只提建议，不擅自扩大修复范围**。
5. 修完跑门禁。

## 合并（旧记录被完全取代）

前置条件，缺一不可：

- 保留旧记录的**每一个**独有理由、备选、后果、验证要求和已点名的覆盖缺口；
- 修复所有入链；
- 不完全取代不算——部分取代要保留两篇并互链。

**绝不把旧文件改写成它的反面。**

## 归档

1. 确认三条：决策已完成、不太可能再指导未来工作、历史理由仍值得保存。
2. `git mv` 整个文件夹（或既有扁平三件组）到 `archived/<class>/`（路径里没有 `implemented` 层）。
3. 状态行保持 `状态：已落地`，下一行插入 `归档：YYYY-MM-DD`。
4. 修复入链——指向归档记录的链接，要么改指当前权威，要么明确标注「历史快照」。
5. 之后永久冻结：不编辑、不翻译、不重排、不移动、不删除。

归档判断是语义的，不是字数或年龄。找不到归档理由但也不值得留下的，按契约「implemented → 删除」处理。

## bootstrap（从旧台账迁移）

1. 识别旧文档里已成形的决策，逐条结构化。
2. 取首次提出日期——优先从 git 历史取，取不到时用旧台账里的动因日期。
3. 按「新增」逐条建记录；旧台账按**只读历史**保留，不删除。
4. 补齐代码锚点：全仓搜索旧编号引用，改为记录路径。
5. 重写 `AGENTS.md` 为地图形态：点名已装的契约与决策树，保留既有项目指令，冲突显式暴露而不是覆盖。
6. 跑门禁，把断链逐条修掉。

## 提交前

三条门禁必须按序全部通过（配对 → 文档 → 链接）；具体命令与路径见 gate 与 bilingual 组件安装的 `AGENTS.md` 块，双语配对门禁只在 bilingual 组件已安装时存在。**每次运行末尾都会列出未自动检查项**——`J1–J3` 见[评审清单](/.agents/se/contracts/review-checklist.zh.md)，`J4` 见[锚点约定](/.agents/se/contracts/anchor-convention.zh.md)，自己再过一遍。

## 边界

- 不改业务逻辑；孤儿特化只提重构建议。
- 记录不收工作项或路线图。非约束性讨论与作者回复是明确允许的证据，分别为 `discuss-<topic>` / `reply-<same-topic>` 三件组，按格式契约 E1–E6、C 组与 X1–X5 校验，不把证据当新决策。
- 提交信息带上决策引用路径。
