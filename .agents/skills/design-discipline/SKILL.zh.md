# design-discipline：设计检查

[English](/.agents/skills/design-discipline/SKILL.md) | 中文

设计层的检查，不替代 lint、类型检查或语言层 code review。经典规则只有在能改善**决策追踪、可验证性、评审效率、修订范围**时才适用。

读取记录时遵循[工作流契约](/.agents/se/contracts/workflow.zh.md)：请求文件夹里只有 `proposal` 配对是记录，`discuss-*` / `reply-*` 是非约束性证据；最终批准在人与提案作者的直接对话中。评审贡献与回复格式见[记录格式契约](/.agents/se/contracts/note-format.zh.md)，只读技能不改证据或记录。保留分歧，不把作者回复或门禁通过当作审阅者确认。

## 四个问题

一个单元（模块 / 类 / 函数组）健康的标准是这四个都答得上来：

1. 决策锚点能清楚落到代码区域吗？
2. 测试能从约束写出来，而不是照着实现补出来？
3. diff 能按意图分块，让人容易审阅吗？
4. 约束变化时，受影响的范围可控吗？

**一个单元最好对应一个可以独立验证的约束。** 不要为了追求短小，把一个连贯流程拆成七个文件——**责任融合才是问题，行数不是。**

## 检查项

1. **边界对应约束**：单元是否只承担一类决策或契约？测试能否脱离实现细节写？改动能否独立成一个 diff？多个决策挤在同一位置 → 拆分信号。
2. **依赖单向**：依赖图无环，下层不依赖上层。
3. **三次再抽象**：同构逻辑出现第三次再考虑抽象。先判断它们会不会随同一条决策一起变化——会的话别抽。
4. **副作用推到边界**：核心逻辑尽量脱离 IO、时钟、随机性，才可验证。
5. **不吞错误**：错误要么处理、要么上抛、要么明确说明为什么可以忽略。空 catch 必须点名错误和忽略理由。
6. **每个构造都有来源**：找不到对应需求或决策的「以后可能用到」代码应当删除。
7. **名字便于检索**：名称应能预测内容，搜索名称能找到相关实现。
8. **能交给工具的交给工具**：格式、lint、类型检查不要占用人工审阅时间。

## 测试的来源

**从决策派生的测试是守卫；从实现倒影的测试只是实现的自拍照。**

写完代码再补的测试只能说明「实现自洽」，不能说明「符合意图」。所以：

- 写测试前先读记录里的 `## 决策` 和 `## 作用域`，从约束推出用例；
- 测试变红时只有三条合法出路：改实现、走 `decision-revise` 改决策、说明测试本身错了。**「把测试改绿」是漂移制造术。**

## 人工审议门

设计讨论的载体是决策树 `proposed/` 生命周期下的提案记录——**它就是设计文档**。新域或复杂机制另写长设计文档时，放在项目自己的 `docs/` 并在提案的 `## 提案` 段落链接过去。

设计完成后，把审议材料整理给用户，**状态标记为 `pending-human-review` 并暂停**。审议包至少包含：

- 提案记录路径 + 版本
- 关联决策（链接）
- 模块边界与依赖方向
- 调用链或数据流
- 关键取舍与备选（对应记录的 `## 考虑过的替代方案`）
- 关键假设
- 验收标准
- 未决问题与潜在漂移点

**只有用户明确批准这个具体版本**（例如「批准这个设计，开始实现」），才能进入编码。

用户要求修改时，状态变为 `changes-requested`，改完**递增版本**重新进入 `pending-human-review`。**不要在同一轮顺手实现。**

批准只针对具体版本。获批后若改变接口、数据模型、边界、流程或验收标准，**都要重新审议**。

## 边界

- 本技能管设计结构；`decision-check` 管改动触碰哪些决策。两者互补，不互相替代。
- 检查结论不能代替用户批准。
- 评审 diff 时发现问题就报告，不擅自扩大修复范围。
