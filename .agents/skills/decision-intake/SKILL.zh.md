# decision-intake：需求准入

[English](/.agents/skills/decision-intake/SKILL.md) | 中文

这个技能处理「要不要做、要满足什么」，发生在写代码之前。需求通常只是一个方向——「更快」「不想引入重依赖」「加个自动补采」——先把它整理成可以判断的约束，再和现行决策对照。

**只读。不改代码，不直接改记录。**

读取记录时遵循[工作流契约](/.agents/se/contracts/workflow.zh.md)：请求文件夹里只有 `proposal` 配对是记录，`discuss-*` / `reply-*` 是非约束性证据；最终批准在人与提案作者的直接对话中。评审贡献与回复格式见[记录格式契约](/.agents/se/contracts/note-format.zh.md)，只读技能不改证据或记录。保留分歧，不把作者回复或门禁通过当作审阅者确认。

## 第一步：读真值

先读[记录格式契约](/.agents/se/contracts/note-format.zh.md)了解记录格式，再遍历决策树 `proposed/` 与 `implemented/` 生命周期下的全部记录。

**不要用记忆代替记录。** 如果决策树不存在，说明冲突面目前不可见，报告这一点并建议先跑 `decision-revise` 的初始化，不要凭空推断。

`rejected/` 里的记录按需查阅——它们是「疫苗」，只有当本次需求正好是当初被否掉的那个方向时才需要读。

## 第二步：把需求写成候选判断

需求是压强，判断是约束。把用户的话翻译成「不得……」的形式，逐条交给用户确认：

| 用户说 | 候选判断 |
|---|---|
| 「能不能加个定时补采」 | 「主动式补采必须是独立进程，不得进入守护循环」 |
| 「日志太吵了」 | 「生产日志只记计数与结构，不记内容」 |

**软偏好不要伪装成普遍规律。** 偏好可以影响选择，但要在报告里注明它是性能、隐私、维护性还是个人口味。

## 第三步：对照作用域

逐条读现行决策的 `## 作用域` 一节，判断候选判断是否落在管辖范围内。**没有锚点不代表没有约束**——新代码永远不会带锚点。

对每条命中的决策给出结论：

| 结论 | 含义 |
|---|---|
| **冲突** | 新判断与现有约束不能同时成立 |
| **受限** | 可以满足，但实现方式会被现有约束塑形 |
| **无碍** | 在作用域内，但两者相容 |

## 第四步：冲突出路，严格按序

找到冲突时，按这个顺序找路，**把每条路都写出来**，不要只给推荐方案：

1. **并存构造**——设计一个让双方都成立的方案。写清草图和它的代价。这是最优解，因为它不动决策集。
2. **修订判断**——说清要改哪条决策、为什么改、会留下什么后果。交给 `decision-revise` 落地，走提案流程。
3. **拒绝需求**——说清哪一方不能让。反复出现的拒绝可以沉淀为「非目标」。

## 第五步：报告

固定结构：

```markdown
intake：<需求一句话>

候选判断：
  - <不得……>
  - <不得……>

命中决策：
  <决策链接>  冲突 —— <依据>
  <决策链接>  受限 —— <依据>
  <决策链接>  无碍

出路（按序）：
  1. 并存构造：<草图 + 代价>
  2. 修订判断：<改哪条、为什么、后果>
  3. 拒绝需求：<哪一方不能让>

建议：<需要新决策 / 需要修订 / 可直接实现>
```

无命中时输出一行 `intake：无冲突` 并给出新决策草案。

## 边界

- 不写代码，不直接改记录。
- 不替用户裁决价值冲突——并列双方动因和代价，然后停下。
- 需求不单独生成第二本账：接受的需求进入它驱动的决策动因，拒绝的需求进入修订推理或非目标。
- 判定「这算不算新决策」用到 `J1`，见[评审清单](/.agents/se/contracts/review-checklist.zh.md)。
